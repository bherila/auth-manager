# Upgrading to 0.1.4

Version 0.1.4 updates the provider and the embedded Composer source archive from
0.1.3. Both packages contain the matching compiled frontend. The shared PHP
dependency is `bherila/auth-laravel ^0.28.6`; the existing browser dependency and
its integrity pin remain unchanged.

## Changes since 0.1.3

- Optional trusted browsers can stand in for the emailed factor after a verified
  password. This is off by default (`AUTH_MANAGER_ALLOW_TRUSTED_DEVICES=false`)
  and only applies when a code follows the password. It reports password-only
  assurance, never refreshes proof for passkey enrollment, and cannot satisfy a
  request for a fresh emailed factor. See [sign-in settings](../deployment.md#sign-in-methods).
- [Portable directory archives](../portable-directory.md) preserve exact subjects,
  compatible password hashes, same-RP passkeys, provider roles, registrations,
  grants and invitation business state. Export/import are explicit operator
  commands; imports default to dry-run and require a fresh directory. Tokens and
  sessions are excluded. Review the documented authentication-assurance and
  invitation-link limitations before moving a directory.
- Authorization responses include the validated issuer under RFC 9207, including
  mounted issuers. Existing redirect validation, client grants and resource
  boundaries remain in force.
- Passkey sign-in honors the current remember-me choice. A restored remember
  cookie does not count as recent authentication or refresh an old credential
  generation.
- [Provider administrator controls](../account-management-contract.md#provider-administrator-management)
  support promotion and demotion after recent proof, with audited actor/target,
  stale-confirmation checks and transactional last-active-administrator guards.
  Disable/delete and the operator role command share those recovery safeguards.
  Provider authority remains separate from application permissions and grants.
- Browser credential-generation checks use the session guard, while bearer
  credentials keep their independent generation checks. Password modes use
  shared credential preflight before opening any session or deciding whether a
  second factor or trusted browser applies.
- Embedded two-factor confirmation/report route names and generated email/form
  URLs have their own `auth-manager.two-factor.*` namespace. A host can keep its
  default `bherila-auth.two-factor.*` routes, including with a route cache.

Password-only sign-in remains the default: code-after-password is `false`,
code-only sign-in is `true`, and trusted browsers are `false`. Enabling any
optional behavior requires deployment configuration; upgrading does not create
accounts, grant application access, import a directory or change sign-in policy.

## Deployment and schema

Two new migrations have shipped since 0.1.3:

| Migration | Purpose |
| --- | --- |
| `2026_11_03_000000_create_trusted_devices_table.php` | Hashed trusted-browser tokens, expiry and credential generation |
| `2026_11_05_000000_create_directory_imports_table.php` | Singleton receipt preventing conflicting or repeated directory imports |

Back up persistent data and configuration, review the release and migration plan,
and apply schema before activating the new code through the deployment pipeline.
A standalone deployment runs its normal provider migrations. An embedded host
runs `php artisan auth-manager:migrate --force --no-interaction` separately from
its own migrations; the host's ordinary migration command does not apply the
provider schema. Preserve the provider's signing keys, session configuration,
table prefix and persistent storage. No account cutover or import runs as part of
these migrations.

Rebuild configuration and route caches as part of code activation. A route cache
created before this upgrade contains the old shared two-factor names and must
be regenerated; keep the same namespace at registration and at request time.
Verify password/code and passkey sign-in, both host and provider confirmation and
report links when embedded, and existing application OAuth callbacks before
opening traffic.

Use the tagged release's `SHA256SUMS-source` and GitHub build provenance before
installing the Composer ZIP, or `SHA256SUMS` for the standalone tarball. See
[release verification](../releases.md#verifying-a-release) and
[embedded packaging](../embedded-mode.md#packaging). A Composer `package`
repository must repeat the archive's actual `require`, `autoload` and
`extra.laravel` metadata and pin the archive checksum and exact release version.

Rolling code back does not undo migrations, restore deleted identities or revoke
credentials issued after the upgrade. Restore data only through the deployment's
reviewed recovery procedure.
