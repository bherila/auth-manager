# Upgrading to 0.1.8

Version 0.1.8 adopts auth-laravel 0.30 and the shared bwh-auth 0.6.5 passkey
confirmation UI. The provider's identity, authorization, issuer and RP bindings
remain unchanged. This release closes the shared email-link second-factor bypass
and supports password or user-verified existing-passkey confirmation when passkey
management needs fresh proof. Provider-specific MFA and administrator authority
checks remain independent.

## Schema and email links

The additive `2026_11_15_000000_add_link_secret_hash_to_two_factor_attempts.php`
migration adds a nullable SHA-256 link-secret hash to the configured two-factor
attempt table. It is included in both provider archives. Standalone deployments
run it through their normal reviewed migration phase; embedded deployments run it
through `auth-manager:migrate` on the provider connection and table prefix. A host
that also uses auth-laravel owns a separate migration for its own attempt table.
Do not copy host attempts, sessions or credentials into the provider.

The public challenge token cannot complete email-link sign-in. Confirmation and
suspicious-report links require the separate secret that only the sent email
carries. Previously sent links stop working after upgrade; their codes remain
valid until normal expiry. A token-only report withdraws the attempt without
claiming that the mailbox owner reported a suspicious sign-in. Without the new
column, code sign-in remains available and emails contain no confirmation/report
buttons. Custom mail views must tolerate nullable link URLs.

## Browser and credential policy

The shared passkey component responds to HTTP 423 by offering current-password
or an existing user-verified passkey confirmation, then retries the requested
ceremony. Confirmation URLs use the server-rendered mount prefix, including in
embedded mode. Keep packaged compiled assets aligned with the PHP release.

The provider retains its ten-minute passkey-management proof window, active
account and credential-generation checks, trusted-browser second-factor policy,
WebAuthn origin/RP binding, credential restrictions and rate limits. A password
confirmation never turns a trusted-browser password-only sign-in into MFA or
provider-administrator proof.

## Rollout and rollback

Qualify the exact provider release before upgrading relying applications. Verify
the source ZIP or standalone archive checksum and provenance as described in
[provider releases](../releases.md). Consumers must update their own lockfiles,
compiled assets and embedded migration plan rather than changing sign-in modes
or linking accounts by email.

A code rollback does not undo schema additions, expired links or account changes.
Keep the nullable column in place and retain a code-based recovery path. Returning
to a release with the known token-only confirmation defect is not a safe rollback;
choose a reviewed release that retains the secret check.
