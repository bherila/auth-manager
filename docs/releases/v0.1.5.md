# Upgrading to 0.1.5

Version 0.1.5 adds an operator-owned lifecycle for synthetic browser-test logins
and records account/security and identity-lifecycle acceptance evidence. Ordinary
accounts retain their configured sign-in policy. The shared PHP and browser
package versions remain unchanged from 0.1.4.

## Synthetic test logins

Use the dedicated `auth-manager:test-logins` command documented in
[test logins](../test-logins.md). Creation requires a permitted testing address,
an explicit future UTC expiry, one or more eligible static OAuth clients, and a
new private credential file. The generated password is delivered once to that
file; console status and audit records contain no password. No ordinary account
is converted into a test login through an HTTP request or mass assignment.

Flagged logins use password-only assurance when they skip the emailed factor.
They cannot use that sign-in to satisfy a request for MFA, gain provider
administrator authority, or authorize clients outside their explicit static
grants. Expiry denies provider authentication immediately; scheduled cleanup
also disables expired accounts and invalidates their credentials. Consumer
session enforcement retains the existing contract's freshness bound rather than
an instantaneous cross-application revocation guarantee.

Extend, disable and retire operate only on flagged identities. Extending does
not enable a manually disabled account; extending after expiry invalidates old
credentials before another sign-in. Retirement uses the same tombstone and
reconciliation lifecycle as ordinary directory deletion and never reuses the
subject. Live synthetic accounts must be retired before exporting them through
an archive format that does not preserve their expiry. Retired records retain
normal deletion and tombstone semantics.

## Schema and activation

The new migration is
`2026_11_07_000000_add_test_login_lifecycle_to_users_table.php`. It adds the
synthetic-login flag and nullable expiry with defaults that leave existing
accounts ordinary. It creates no identity, grant or test credential.

Review the migration and apply schema through the deployment's normal reviewed
migration phase before activating the new code. An embedded host runs the
provider's own migration command separately from its application migrations;
see [embedded mode](../embedded-mode.md). Rebuild configuration and route caches
as part of activation, retain the provider's existing storage and signing keys,
and keep the normal scheduler running. Deploying this release does not create
test accounts or run an account cutover.

## Account-management acceptance

The [acceptance audit](../account-management-acceptance.md) distinguishes shipped
provider behavior, shared/in-process fixtures, and evidence still required from
each consuming application. Existing account and lifecycle screens are reused.
The audit does not certify a deployed consumer, retire its local forms, approve
its local cascade, or replace its emergency-access and outage acceptance.

## Verify the release

Verify the tagged release's checksums and build provenance before installation;
see [release verification](../releases.md#verifying-a-release). The Composer
source ZIP includes its matching compiled frontend. Updating a dependency does
not perform a live identity migration. Code rollback does not restore deleted
identities or undo schema changes and requires the operator's reviewed recovery
procedure.
